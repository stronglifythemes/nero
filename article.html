Write a release checklist people actually use

A release checklist only helps if it is short enough to follow. Here is how we keep ours useful.

Most release problems are not hard bugs. They are small steps that someone forgot because the process lived in one person's head.


This note describes how we write checklists with the teams we work with. To learn more about Nero, visit our about page.



Start from the last incident


Before writing a new checklist, look at recent releases and ask:


  • Which step was skipped or done late.
  • Which check would have caught it.
  • Who should own that check next time.


Keep it short


A long checklist gets skimmed. Keep the steps that prevent real problems and automate the rest.




If a step can be automated, it should not be on the checklist.





Laying out each step makes gaps in the process easier to see.




Make it part of the workflow


A checklist works when it lives where the work happens:


  • Keep it in the repository, next to the code.
  • Link it from the release pull request.
  • Review it after every incident.

Treat the checklist like code: small, versioned and updated whenever the process changes.
